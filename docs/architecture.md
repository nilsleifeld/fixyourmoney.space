# Static Site Generator Architecture

## Overview

The project uses a small static-site generator written with the Go standard library. It renders localized Go templates, validates translation completeness, copies one immutable static release tree, and atomically publishes the result to `dist/`.

```sh
go run . build
go run . build -verbose
go run . serve -addr :8080
go run . serve -verbose
```

There is no bundler, client-side i18n, plugin system, or runtime content generation. `legacy/` is reference material and is never read by the generator.

## Source structure

```text
pages/                          route-defining page templates
  index.md                      localized AI-agent content template
  llms.txt                      default-locale LLM content template
templates/                      shared layout and structural partials
i18n/<locale>.json              flat, build-time translations
static/
  css/site.css                  stylesheet entry point
  css/tokens.css                shared base, semantic, and component tokens
  css/themes/memphis/           sole concrete modular theme
  fonts/                        local fonts
  js/site.js                    JavaScript module entry point
  js/components/                progressive component modules
internal/generator/             reusable build implementation and tests
dist/                           generated output; never edit manually
```

## Configuration

`site.json` provides:

- `title`: site name available as `.Site.Title`;
- `baseURL`: origin used for canonical and alternate URLs;
- `twitterCreator`: account used in Twitter metadata;
- `defaultLocale`: root redirect and translation reference locale;
- `locales`: locales generated by the build.

The default locale must occur exactly once in `locales`. Locale codes must be valid path segments.

## Build sequence

`generator.Build(source, output)` performs these steps:

1. Resolve and validate source/output paths and `site.json`.
2. Load every active locale and require exactly the same translation-key set as the default locale.
3. Discover pages and shared templates.
4. Create a temporary output directory next to the final output.
5. Calculate and copy the static release tree.
6. Render every HTML page for every active locale.
7. Render `pages/index.md` for every locale and publish its default-locale result as `/index.md`.
8. Render the independent `pages/llms.txt` template in the default locale as `/llms.txt`.
9. Write the sitemap, robots file, and root redirect.
10. Replace `dist/` only after every earlier step succeeds.

A failed build leaves the previous successful output untouched.

## Development server and live reload

`go run . serve` performs an initial build and polls the build inputs for changes. It watches `site.json`, JSON files in `i18n/`, Go page templates plus `pages/index.md` and `pages/llms.txt`, Go templates in `templates/`, and all files in `static/`. Changes are briefly debounced before another atomic build.

The development server injects a live-reload client into served HTML responses only; generated files in `dist/` and production builds remain unchanged. The client keeps a server-sent events connection open and reloads the page after a successful rebuild. Failed rebuilds are logged, keep the previous output intact, and do not reload the browser. Browser caching is disabled while using the development server so rapid rebuilds cannot return stale HTML.

## CLI logging

Both commands use structured `log/slog` records rendered by a human-readable text handler rather than JSON. Interactive terminals receive concise colored status symbols; redirected output and CI logs remain plain text. On GitHub Actions, error records additionally emit a workflow error annotation. A normal build reports its source, output, duration, localized page count, asset count, and locale count.

Use `-verbose` or `-v` to include resolved paths and each build phase: configuration loading, translation validation, template discovery, static release copying, localized rendering, and publishing. In serve mode, the logger also reports a compact summary of changed files and emits one detailed record per file in verbose mode. Errors retain the previous successful output and include a hint to rerun with verbose diagnostics.

## Routes and rendering

Page paths define locale-relative routes:

| Source | Logical route | English output |
|---|---|---|
| `pages/index.gohtml` | empty | `dist/en/index.html` |
| `pages/datenschutz.gohtml` | `datenschutz` | `dist/en/datenschutz/index.html` |
| `pages/help/contact.gohtml` | `help/contact` | `dist/en/help/contact/index.html` |

Each page defines `content`, `page-title`, and `page-description`, then executes `layout`. Shared templates provide the document shell, header, footer, chart groups, and consent dialog. `html/template` escapes dynamic values by default.

Template data contains `.Site`, `.Page`, `.Locale`, and `.Locales`.

### AI-agent output

`pages/index.md` is rendered with `text/template`, preserving translated text without HTML escaping. The build creates `/<locale>/index.md` for every configured locale and publishes the default-locale rendition at `/index.md`. The independent `pages/llms.txt` template is rendered only in the default locale and published at `/llms.txt`; projects can therefore give it different content. In this project both source templates intentionally contain the same content. The localized HTML home page advertises its Markdown counterpart with a `text/markdown` alternate link.

### Template functions

- `t "key"`: translated string for the current locale. Active locales have already passed exact key-set validation.
- `asset "path"`: immutable public URL for a file below `static/`; unknown files fail the build.
- `url "route"`: current-locale URL.
- `languageURL "de"`: same logical route in another active locale.
- `canonicalURL`: absolute URL of the current page.
- `languageCanonicalURL "de"`: absolute alternate URL.
- `languageName "de"`: native display name for supported locales.
- `markdownURL`: absolute URL of the localized Markdown home page.
- `textDirection`: `rtl` for Arabic and `ltr` otherwise.

The Markdown index additionally provides `pageURL` and `languageMarkdownURL "de"`.

## Static release hashing

Static files can depend on each other through relative URLs and module imports. The generator therefore hashes the entire tree as one release instead of hashing files independently:

1. Collect all regular files below `static/` and sort by slash-normalized path.
2. Feed each path length, path, content length, and content into SHA-256.
3. Use the first 12 hexadecimal characters as the release hash.
4. Copy every file to `/static/<release-hash>/<original-path>`.
5. Resolve every `asset` call to that same release base.

Consequently these relationships continue to work after publishing:

- `site.css` → relative CSS `@import`;
- theme entry point → theme modules;
- CSS modules → relative font/image `url(...)` values;
- `site.js` → relative ES-module imports.

Any static-file change creates a new release base. Symbolic links remain unsupported and fail the build.

## Client-side enhancement and privacy

Core content, links, disclosures, and chart explanations are usable without JavaScript. Local ES modules progressively add:

- native impact dialogs;
- ARIA tabs and keyboard navigation;
- a user-controlled hero perspective;
- consent persistence and the `consentchange` event;
- lazy TradingView charts after `externalMedia` consent;
- Plausible Analytics loaded unconditionally.

No TradingView element is present in generated HTML. Its external URL is assigned only after `externalMedia` consent. Consent expires after 60 days; blocked storage falls back to in-memory state without breaking the page.

## Validation

Run before completing changes:

```sh
go test ./...
go vet ./...
go run . build
```

Tests cover live-reload injection and source watching as well as localized routes, release hashing and relative dependencies, metadata/RTL helpers, translation-key parity, unknown assets/translations, and static symlink rejection.
