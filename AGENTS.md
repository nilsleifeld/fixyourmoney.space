- Use strict BEM naming for component CSS classes: `.block`, `.block__element`, and `.block--modifier` / `.block__element--modifier` (for example `.card`, `.card__title`, `.card--featured`).
- Use lowercase kebab-case for every BEM name. Blocks must be independent, reusable components; elements belong to their block; modifiers represent variants, sizes, or states.
- Never mirror the DOM hierarchy in class names or chain element names (avoid `.card__header__title`); use `.card__title` or introduce a new block instead.
- Prefer single BEM class selectors to keep specificity low. Avoid styling components through IDs, HTML tags, deeply nested selectors, or ambiguous global classes, and do not use modifier classes without their corresponding block or element class.
- Build the entire design system on the design tokens defined in `static/css/tokens.css`; do not hard-code design values in component styles when a token can represent them.
- Follow this token hierarchy:
  1. **Base tokens** are the primitive values (for example colors, spacing, typography, radii, and shadows) and are the single source of truth.
  2. **Semantic tokens** reference base tokens with purpose-driven names (for example `--color-text-primary` or `--space-section`) and must not duplicate raw values.
  3. **Component tokens** reference semantic tokens whenever possible, or base tokens when no meaningful semantic token exists, and describe component-specific decisions (for example `--button-background` or `--card-radius`).
- Define new or changed tokens in `static/css/tokens.css`, compose token layers with `var(...)`, and reuse existing tokens before introducing new ones.
- Derive spacing and spatial size values from the base token `--spacing` using `calc(...)` (for example `calc(var(--spacing) * 4)`) instead of hard-coding values. This applies to values such as padding, margin, gap, width, height, and component dimensions; use dedicated typography, radius, or other domain-specific tokens where appropriate.
- Build interfaces on established web standards and prefer native, semantic HTML over custom JavaScript implementations. Use the `<dialog>` element for dialogs and the `<details>` and `<summary>` elements for disclosure widgets whenever they fit the required behavior.
- Whenever writing JavaScript, document all functions, classes, methods, parameters, return values, and relevant types with JSDoc. Add concise inline comments for non-obvious logic, assumptions, edge cases, and workarounds; avoid comments that merely restate self-explanatory code.

## Static site generator

- This website is generated by a small Go application that uses only the Go standard library. `main.go` provides the CLI and local HTTP server; the reusable build implementation and its tests live in `internal/generator/`.
- Run `go run . build` to generate the site and `go run . serve` to build it, watch source files, and reload connected browsers after successful rebuilds. Supported options are `-source`, `-output`, `-verbose`/`-v`, and, for `serve`, `-addr` (for example `go run . serve -addr :8080 -verbose`).
- Use structured `log/slog` records for CLI and generator diagnostics. Render them through the human-readable non-JSON console handler in `internal/consolelog/`; normal output should stay concise, while verbose output should expose build phases and individual watched-file changes for local and CI debugging.
- Treat `dist/` as generated output and never edit it by hand. Make website changes in `pages/`, `templates/`, `i18n/`, `static/`, or `site.json`. The `legacy/` directory is ignored by the generator.
- The build reads and validates `site.json`, loads translations, discovers pages and shared templates, hashes and copies static assets, renders every page for every configured locale, creates the root redirect, and atomically replaces `dist/` only after all steps succeed. A failed build leaves the previous successful output intact.

## Site configuration and locales

- Define global metadata and languages in `site.json`. `.Site.Title` comes from `title`; `defaultLocale` is the translation fallback and the root redirect fallback when the browser language is unsupported; `locales` controls which localized sites are generated.
- Keep `defaultLocale` in `locales`, use valid unique locale codes, and provide `i18n/<locale>.json` for every configured locale.
- Translation files are flat JSON objects whose values are strings. All translations are rendered into HTML at build time; do not add client-side i18n unless the architecture is intentionally changed.
- Use `{{ t "translation.key" }}` for translated text. Resolution checks the current locale first and the default locale second; the build fails when both are missing.

## Pages, routing, and templates

- Add pages as `.gohtml` files under `pages/`. File paths define routes: `pages/index.gohtml` becomes `/<locale>/`, `pages/about.gohtml` becomes `/<locale>/about/`, and `pages/help/contact.gohtml` becomes `/<locale>/help/contact/`. Each output is written as an `index.html` below that route.
- Avoid page paths that resolve to the same route; route collisions fail the build. The generator also creates `dist/index.html`, which redirects `/` to a supported locale matching `navigator.languages`, or to `defaultLocale` when none match.
- Put reusable Go templates in `templates/`. Pages should define their content blocks and execute a shared layout, for example `{{ define "content" }}...{{ end }}` followed by `{{ template "layout" . }}`.
- Templates use Go's `html/template`, so dynamic values are HTML-escaped by default. Preserve this safety and do not bypass escaping without a reviewed requirement.
- Template data provides `.Site`, `.Page`, `.Locale`, and `.Locales`. Use `.Page.Route` when the current logical route is needed.
- Use `{{ url "route" }}` for internal links in the current locale rather than hard-coded localized URLs. Use an empty route for the home page.
- Use `{{ languageURL "en" }}` (with a configured locale) to link to the same page in another language. Unknown locale codes fail the build.

## Static assets

- Store CSS, JavaScript, images, and other unchanged files under `static/`. Files are copied without bundling, minification, or transformation.
- Always reference static files through `{{ asset "relative/path" }}`. The generator creates content-hashed URLs in the form `/static/<12-character-sha256>/<relative-path>`; changing file contents therefore changes its public URL. Referencing a missing asset fails the build.
- Do not use symbolic links inside `static/`; they are unsupported.

## Validation

- Before completing changes, run `go test ./...` and `go vet ./...`, then run `go run . build` to validate real templates, translations, routes, and asset references.
- Expect builds to fail for invalid or missing configuration, missing locale files or translations, unknown assets/locales, template parse or execution errors, duplicate output routes, or an empty `pages/` directory. Fix the source error rather than modifying generated output.
- Keep the generator intentionally simple unless a task explicitly changes its architecture: there is currently no minification, bundling, front matter, runtime-generated content, plugin system, or external Go dependency.
